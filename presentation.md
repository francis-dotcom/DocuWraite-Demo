# DocuWraite Detailed Sales Demo Script

## How to Use This Script

This is a word-for-word live demo script for presenting DocuWraite to a buyer, provider organization, supervisor team, or operations lead.

This is not a summary.
This is meant to be followed during the actual presentation.

It includes:

- what to say
- what to click
- what to type
- where to pause
- what value to point out
- how to handle common questions
- what to do if the demo takes a different path

If you want to sound natural, do not memorize every sentence exactly. Use the structure, key phrases, and transitions.

---

## Demo Objective

The objective of this presentation is to show that DocuWraite is not just a documentation form.

It is a guided documentation workflow that helps:

- DSPs document more consistently
- supervisors enforce better note quality
- teams improve handoff
- organizations create cleaner records for QA and compliance

Your central sales message should be:

`DocuWraite is guided documentation, not just a text box.`

Repeat that idea throughout the presentation.

---

## Suggested Demo Length

- Full presentation: 20 to 30 minutes
- Short version: 10 to 12 minutes
- Fast executive summary: 5 minutes

This script is written for the full version.

## Before You Present

### Prep checklist

- Make sure the app is open and stable.
- Make sure you know which client profile you will use.
- Make sure the documentation session can be opened cleanly.
- Make sure Notes Library already contains at least one sample note.
- Make sure the handover flow works end to end.
- Make sure the PDF/export or new-window preview opens correctly.
- Make sure the DSP signature field is visible during the demo.
- Make sure you know what example note details you will type.

### Best practice

Do not improvise the documentation content too much.
Use one consistent story for the shift.

For example, use a scenario like this throughout the demo:

- oxygen checks were due
- supervision and cueing were provided
- no acute distress was observed
- there was some follow-up need for the next shift
- vitals may need to be included in handover

That gives you enough substance to demonstrate the product without creating a messy story.

---

## Core Sales Message

Keep returning to these four points:

1. Staff do not have to remember everything at the end of the shift.
2. The software guides documentation before the note is generated.
3. Final case note and handover are treated as two different workflows.
4. The output becomes review-ready, not just saved text.

## Optional Buyer Questions and Suggested Answers

## If they ask: "Is this replacing the DSP?"

Say:

"No.
The DSP still provides the real facts.
The platform helps structure those facts and improve note quality.
The system is there to guide, not replace, staff judgment."

## If they ask: "Is the AI making things up?"

Say:

"The workflow is designed so that documentation comes from actual shift facts first.
The note-generation layer is supposed to organize and strengthen those facts, not invent events."

## If they ask: "What if staff skip details?"

Say:

"That is exactly why the structured prompts, draft context questions, validation steps, and handover workflow matter.
The product is designed to reduce missing detail before submission."

## If they ask: "Why separate final case note and handover?"

Say:

"Because they serve different functions.
The final case note documents the shift for the record.
The handover note supports the next shift.
Combining them usually weakens both."

## If they ask: "What is the supervisor value?"

Say:

"The supervisor value is cleaner input, less correction work, clearer identity on the note, and a better review trail in the Notes Library."
